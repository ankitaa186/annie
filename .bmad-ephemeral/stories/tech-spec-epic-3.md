## Overview

Epic 3 integrates the agentic-memories service to enable persistent memory of user conversations, decisions, and preferences. This epic builds upon the foundation established in Epics 1 and 2 (infrastructure, chat API, LLM integration, state management) to create a memory layer that allows Annie to provide context-aware, personalized decision support.

The core value proposition is transforming Annie from a stateless chatbot into an intelligent companion that remembers past interactions and uses that context to inform future recommendations. This addresses the PRD goal of enabling 80% trust in Annie's advice by making recommendations based on user history, preferences, and outcomes rather than treating each conversation in isolation.

## Objectives and Scope

**In Scope:**
- MCP tools for memory operations (`store_memory`, `retrieve_memories`)
- Integration with agentic-memories HTTP API
- Conversation summarization and storage triggers
- Memory retrieval with relevance ranking
- Graceful degradation when agentic-memories unavailable
- Redis fallback for temporary memory storage during outages
- Performance monitoring (<300ms retrieval, <500ms storage per PRD)
- Memory context injection into LLM prompts for personalized advice

**Out of Scope:**
- Long-term persistence layer (PostgreSQL) - deferred to post-V1
- Memory pruning/archival strategies - deferred
- User-facing memory management UI - deferred to Epic 5 (Telegram bot enhancements)
- Cross-user memory sharing or aggregation
- Memory encryption at rest (relies on agentic-memories service implementation)
- Memory versioning or rollback capabilities

## System Architecture Alignment

This epic aligns with the MCP-based architecture established in the Architecture Plan:

**Components Referenced:**
- **MCP Server** (`mcp_server/`): Hosts `store_memory` and `retrieve_memories` tools
- **Backend API** (`backend/`): Orchestrates memory operations during conversation lifecycle
- **Redis**: Provides fallback storage when agentic-memories unavailable
- **agentic-memories** (External Service): Primary memory persistence layer

**Architectural Constraints:**
- Must use MCP protocol (JSON-RPC 2.0) for tool calls per Epic 2 patterns
- Memory operations async/non-blocking to meet <2s response time constraint
- Graceful degradation required per Architecture NFRs (99%+ uptime)
- Integration via HTTP client (existing `httpx` dependency from Epic 2)

**Data Flow:**
```
User Message → Backend API → LLM (with memory context)
                    ↓
            MCP Server (retrieve_memories)
                    ↓
            agentic-memories API
                    ↓
            Retrieved memories → LLM context
```

```
Conversation End → Backend API
                       ↓
                MCP Server (store_memory)
                       ↓
                agentic-memories API
                       ↓  (if fails)
                Redis (temporary storage)
```

## Detailed Design

### Services and Modules

| Service/Module | Responsibility | Inputs | Outputs | Owner |
|---------------|---------------|---------|---------|-------|
| `mcp_server/tools/memory.py` | Implements `store_memory` and `retrieve_memories` MCP tools | JSON-RPC requests from Backend | Tool execution results | MCP Server |
| `mcp_server/clients/agentic_memories_client.py` | HTTP client for agentic-memories API | Memory objects, queries | API responses, errors | MCP Server |
| `backend/api/memory_manager.py` | Orchestrates memory operations, fallback logic | Conversation context, user_id | Success/failure status | Backend API |
| `backend/api/routes/chat.py` (enhanced) | Triggers memory storage on conversation end | User message, conversation state | None (async operation) | Backend API |

| Redis (fallback store) | Temporary memory queue when agentic-memories down | Memory objects | Queued memories for retry | Infrastructure |

### Data Models and Contracts

**Memory Object (Core Entity):**
```python
{
  "user_id": str,  # Unique user identifier
  "memory_id": str,  # UUID generated by agentic-memories
  "timestamp": str,  # ISO 8601 format
  "conversation_summary": str,  # LLM-generated summary of conversation
  "decisions": [
    {
      "decision": str,  # What was decided
      "options_considered": List[str],  # Alternatives evaluated
      "reasoning": str,  # Why this choice was made
      "outcome": Optional[str]  # If user provides feedback later
    }
  ],
  "preferences": {
    "risk_tolerance": Optional[str],  # e.g., "conservative", "moderate", "aggressive"
    "priorities": List[str],  # User's stated priorities
    "constraints": List[str]  # Stated constraints or limitations
  },
  "topics": List[str],  # Key topics discussed (for retrieval)
  "sentiment": Optional[str]  # e.g., "positive", "neutral", "concerned"
}
```

**agentic-memories API Contract (HTTP):**

POST `/api/memories`
```json
{
  "user_id": "string",
  "content": {
    // Memory Object as defined above
  },
  "metadata": {
    "source": "annie-v1",
    "tags": ["decision", "financial"]
  }
}
```

Response: `201 Created`
```json
{
  "memory_id": "uuid",
  "status": "stored",
  "timestamp": "ISO 8601"
}
```

GET `/api/memories/query`
```json
{
  "user_id": "string",
  "query": "string",  # Semantic search query
  "limit": 5,  # Top N memories
  "filters": {
    "topics": ["finance", "investment"]  # Optional filters
  }
}
```

Response: `200 OK`
```json
{
  "memories": [
    // Array of Memory Objects with relevance scores
  ],
  "total_count": int
}
```

**Redis Fallback Schema:**
```
Key: memory:queue:{user_id}:{timestamp}
Value: JSON-serialized Memory Object
TTL: 24 hours (for retry mechanism)
```

### APIs and Interfaces

**MCP Tool: `store_memory`**

JSON-RPC Method:
```json
{
  "jsonrpc": "2.0",
  "method": "tools/call",
  "params": {
    "name": "store_memory",
    "arguments": {
      "user_id": "string",
      "conversation_summary": "string",
      "decisions": [...],
      "preferences": {...},
      "topics": [...]
    }
  },
  "id": 1
}
```

Response:
```json
{
  "jsonrpc": "2.0",
  "result": {
    "memory_id": "uuid",
    "status": "stored",
    "fallback_used": false

  "id": 1

```

Error Response (agentic-memories down):
```json
{
  "jsonrpc": "2.0",

    "status": "queued_for_retry",
    "fallback_used": true,
    "redis_key": "memory:queue:..."
  },
  "id": 1
}
```

**MCP Tool: `retrieve_memories`**

JSON-RPC Method:
```json
{
  "jsonrpc": "2.0",
  "method": "tools/call",
  "params": {
    "name": "retrieve_memories",
    "arguments": {
      "user_id": "string",
      "query": "string",

    }
  },
  "id": 2
}
```

Response:
```json

  "jsonrpc": "2.0",
  "result": {
    "memories": [

}
```

**Backend API Enhancements:**

No new public endpoints. Existing endpoints enhanced internally:

- `GET /api/stream/{conversation_id}`: Calls `retrieve_memories` before streaming LLM response

### Workflows and Sequencing

**Memory Storage Flow (Story 3.1):**

1. User sends message indicating conversation end (e.g., "thanks", timeout, explicit end)
2. Backend API detects end trigger in `POST /api/chat` handler
3. Backend calls LLM to generate conversation summary:
   - Input: Full conversation history from Redis
   - Output: Structured summary with decisions, preferences, topics
4. Backend constructs Memory Object from summary
5. Backend calls MCP `store_memory` tool via JSON-RPC
6. MCP Server attempts to POST to agentic-memories API
7. **Success Path**:
   - agentic-memories returns 201 Created with memory_id
   - MCP returns success result to Backend
   - Backend logs successful storage
8. **Failure Path** (agentic-memories unavailable):
   - HTTP timeout or error response
   - MCP stores Memory Object in Redis queue (`memory:queue:...`)
   - MCP returns fallback_used=true to Backend
   - Backend logs warning, user notified: "Memory temporarily cached"
9. **Retry Mechanism** (background task):
   - Periodic job checks Redis queue
   - Retries failed memory storage operations
   - Removes from queue on success

**Memory Retrieval Flow (Story 3.2):**

1. User sends query message via `/api/chat`
2. Backend routes to `/api/stream/{conversation_id}`
3. Before calling LLM, Backend extracts query intent from user message
4. Backend calls MCP `retrieve_memories` tool with:
   - user_id from session
   - query based on message semantics
   - limit=5 (top 5 relevant memories)
5. MCP Server calls agentic-memories `GET /api/memories/query`
6. **Success Path**:
   - agentic-memories returns ranked memories with relevance scores
   - MCP returns memories to Backend
   - Backend injects memories into LLM system prompt:
     ```
     You are Annie. Here are relevant memories from past conversations:
     [Memory 1 summary...]
     [Memory 2 summary...]

     Use these to personalize your advice.
     ```
7. **Failure Path** (no memories or service down):
   - agentic-memories returns empty array or HTTP error
   - Backend proceeds without memory context
   - LLM system prompt includes: "No past memory available"
8. LLM generates response with memory-aware context
9. Streaming response sent to user

## Non-Functional Requirements

### Performance

- **Memory Retrieval**: <300ms p95 (per PRD technical metrics)
- **Memory Storage**: <500ms p95 (per Epic success criteria)
- **LLM Context Building**: Additional <100ms overhead for memory injection
- **Total Response Time**: Maintain <2s p95 overall response time (existing PRD requirement)
- **Concurrent Operations**: Support 100 concurrent memory operations (aligned with existing concurrent streams limit from Story 2.3)
- **Memory Query Limit**: Top 5 memories per retrieval to balance context richness vs. token cost

### Security

- **Authentication**: user_id must match authenticated session (existing session management from Story 2.5)
- **Authorization**: Users can only access their own memories (enforced by agentic-memories service)
- **Data Privacy**: Memory objects contain PII; rely on agentic-memories for encryption at rest
- **API Keys**: AGENTIC_MEMORIES_API_KEY stored in `.env`, masked in logs (existing pattern from Epic 1)
- **Network**: HTTPS required for agentic-memories API calls in production
- **Input Validation**: Sanitize user_id and query parameters to prevent injection attacks

### Reliability/Availability

- **Graceful Degradation**: System continues functioning when agentic-memories unavailable (AC #3, #4 from Story 3.1)
- **Fallback Storage**: Redis queue for temporary memory storage during outages
- **Retry Logic**: Exponential backoff for memory storage retries (max 3 attempts over 24 hours)
- **Timeout Handling**: 5s timeout for agentic-memories API calls to prevent blocking
- **Health Checks**: Monitor agentic-memories availability via periodic health endpoint polling
- **Error Recovery**: System auto-recovers when agentic-memories comes back online (retry queue processing)
- **Target Uptime**: 99%+ (per PRD), unaffected by agentic-memories downtime

### Observability

**Logging (Structured JSON, existing format from Epic 1):**
- Memory storage attempts: `memory.store.attempt` (user_id, conversation_id, timestamp)
- Memory storage success: `memory.store.success` (memory_id, duration_ms)
- Memory storage failure: `memory.store.failure` (error, fallback_used, redis_key)
- Memory retrieval: `memory.retrieve` (user_id, query, retrieved_count, duration_ms)
- Fallback usage: `memory.fallback.used` (operation, reason)
- Retry attempts: `memory.retry.attempt` (redis_key, attempt_number)

**Metrics:**
- Memory operations per second (ops/s)
- Memory retrieval latency (p50, p95, p99)
- Memory storage latency (p50, p95, p99)
- Fallback usage rate (% of operations)
- Retry queue depth (# of pending retries)
- agentic-memories availability (% uptime)

## Acceptance Criteria (Authoritative)

**Story 3.1: Memory Storage Integration**

**AC 3.1.1:** Given agentic-memories service is available, when a conversation ends (user sends "thanks" or conversation times out), then conversation context is stored via `store_memory` tool with:
  - user_id
  - conversation summary
  - key decisions made
  - user preferences expressed
  - timestamp

**AC 3.1.2:** Given memory storage, when I check agentic-memories, then the conversation is stored with proper structure and can be retrieved later

**AC 3.1.3:** Given agentic-memories service is down, when a conversation ends, then the system continues without error, logs the failure, and stores memory in Redis temporarily for retry

**AC 3.1.4:** Given memory storage fails, when I send another message, then Annie continues working without memory context but informs the user: "Note: I'm having trouble accessing your memory right now, but I can still help."

**AC 3.1.5:** Given memory is stored, when I check the stored data, then it includes:
  - Decision context (what decision was made, options considered)
  - User preferences (risk tolerance, priorities)
  - Conversation flow (key topics discussed)
  - Outcomes (if user provides feedback)

**AC 3.1.6:** Given memory storage, when I check performance, then memory storage completes within 500ms (p95)

**Story 3.2: Memory Retrieval for Decision Support**

**AC 3.2.1:** Given a user asks for decision help ("Should I invest in stocks?"), when Annie processes the request, then it retrieves relevant memories via `retrieve_memories` tool with query based on decision context

**AC 3.2.2:** Given retrieved memories, when Annie analyzes options, then it uses memory context in pros/cons analysis, referencing past decisions: "Based on your previous preference for conservative investments..."

**AC 3.2.3:** Given memory retrieval, when Annie provides recommendations, then it references past decisions and outcomes: "Last time you chose X, and it worked well because..."

**AC 3.2.4:** Given no relevant memories exist, when Annie provides advice, then it works without memory context but acknowledges: "I don't have your past decision history yet, but here's my analysis..."

**AC 3.2.5:** Given memory retrieval takes >300ms, when I check performance, then it's logged as a performance issue and optimization is considered

**AC 3.2.6:** Given persona-aware retrieval, when memories are retrieved, then they're filtered by decision-making persona (e.g., "Stock Trader" persona retrieves financial decision memories)

**AC 3.2.7:** Given memory retrieval, when I check relevance, then retrieved memories are ranked by relevance and top 5 most relevant memories are used

## Risks, Assumptions, Open Questions

**Risks:**
1. **Risk**: agentic-memories service downtime impacts user experience
   - **Mitigation**: Redis fallback + retry queue ensures no data loss; graceful degradation maintains functionality

2. **Risk**: LLM conversation summarization quality affects memory usefulness
   - **Mitigation**: Structured prompts with examples for summarization; manual validation during Story 3.1 implementation

3. **Risk**: Memory retrieval relevance may be poor if agentic-memories semantic search is weak
   - **Mitigation**: Test with real conversation data; consider manual tagging as fallback

4. **Risk**: Performance degradation (<300ms retrieval) if agentic-memories is slow
   - **Mitigation**: 5s timeout prevents blocking; monitor p95 latency and optimize agentic-memories deployment if needed

5. **Risk**: Privacy concerns with storing conversation data externally
   - **Mitigation**: Rely on agentic-memories encryption; ensure HTTPS in production; document data handling in privacy policy

**Assumptions:**
1. **Assumption**: agentic-memories service will be deployed and available at `http://host.docker.internal:8080` for local dev
2. **Assumption**: agentic-memories API supports semantic search with relevance ranking (not just keyword matching)
3. **Assumption**: Conversation end detection via "thanks" keyword is sufficient for V1 (more sophisticated detection deferred)
4. **Assumption**: Top 5 memories provide sufficient context without exceeding token limits
5. **Assumption**: Redis 24-hour TTL for retry queue is acceptable (memories older than 24h won't be retried)

**Open Questions:**
1. **Question**: Should we implement conversation end confirmation UI in Telegram bot? (Deferred to Epic 5)
2. **Question**: What's the agentic-memories data retention policy? (Impacts long-term memory strategy)
3. **Question**: Should memory storage be synchronous (blocking) or async? (Proposal: async to avoid latency impact)
4. **Question**: How to handle memory conflicts if user has contradictory preferences over time? (V2 feature)

   - Redis queue operations
   - Coverage target: 80%+ for new code

2. **Integration Tests** (`pytest` with TestClient):
   - End-to-end memory storage flow: Chat → LLM summarization → agentic-memories storage
   - End-to-end memory retrieval flow: Query → retrieve_memories → LLM context injection
   - Fallback scenarios: agentic-memories unavailable → Redis queue → retry
   - Memory persistence: Store → retrieve → verify data integrity

3. **Performance Tests**:
   - Memory retrieval latency: p95 <300ms (10 concurrent users, 100 queries)
   - Memory storage latency: p95 <500ms (10 concurrent users, 50 stores)
   - Load testing: 100 concurrent memory operations
   - Tools: `locust` or `pytest-benchmark`

4. **Manual/Exploratory Tests**:
   - Conversation quality: Verify LLM uses retrieved memories effectively in responses
   - Edge cases: Empty memories, malformed agentic-memories responses
   - End-to-end user flow: Multi-day conversations with memory context

**Test Frameworks:**
- `pytest>=7.4.0` (existing)
- `pytest-asyncio>=0.21.0` (existing)
- `pytest-mock` for mocking agentic-memories API
- `locust` for performance testing (Story 3.2)
