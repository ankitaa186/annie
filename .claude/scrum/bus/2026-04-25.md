## [STATUS] David — Triage: literal `\~` and `\|` rendering in Telegram messages
**Time:** 2026-04-25 (triage, no commit)
**Severity:** P0 user-facing visual bug — every Telegram response with `~` or `|` characters renders literal backslashes to the user. Live, in production. Affects every chat path (streaming first-token, mid-stream edits, message split, final edit, post-media new-message).
**Effort estimate:** 1 hour. One-line escape-list extension + a small unit test. Hotfix-now candidate; does NOT need a drafted story.

### Root cause
**Mismatch between LLM formatting instruction and bot send mode**, with an incomplete escape-stripping helper in the middle.

- `backend/api/prompts.py:150-159` (`TELEGRAM_FORMAT_INSTRUCTIONS`) tells the LLM to format responses as **MarkdownV2** and explicitly to *"Escape special characters (`\_ \* \[ \] \( \) \~ \` \> \# \+ \- \= \| \{ \} \. \!`) outside formatting tags"*.
- `telegram_bot/handlers/message.py` actually sends with `parse_mode=ParseMode.HTML` (lines 621, 644, 667, 675, 722, 1058, 1135) after passing the LLM text through `markdown_to_telegram_html()` (line 161-237).
- That helper at lines 225-235 strips MarkdownV2 backslash-escapes for `\* \_ \` \# \. \- \! \[ \] \( \)` — **11 of the 18 MarkdownV2 special characters**.
- It does NOT strip `\~ \| \> \+ \= \{ \}`. So when the LLM (correctly following its prompt) emits `\~75 cal \| 6g protein`, the helper passes `\~` and `\|` through unchanged. HTML mode does not interpret `\` as anything, so Telegram renders the literal backslashes.

None of these touched the escape logic. The `markdown_to_telegram_html` helper has been in its current form since `a0e90a2` (Dec 14, 2025). **This is not a code regression — the code path has been incomplete for 4+ months. The likely trigger is LLM-side**: the current model (Grok-4 / ChatGPT-5 / Gemini, depending on `LLM_PROVIDER`) is now more strictly following the MarkdownV2-escape directive, producing escapes the bot was never set up to strip.

### Proposed fix — minimal & correct
**File:** `telegram_bot/handlers/message.py:223-235`

Add the seven missing MarkdownV2 special-character escapes to the strip block:

```python
# Clean up escaped characters that markdown uses
# Telegram MarkdownV2 special chars: _ * [ ] ( ) ~ ` > # + - = | { } . !
# (html.escape already handled &, <, > so we just need backslash escapes for the rest)
text = text.replace(r'\*', '*')
text = text.replace(r'\_', '_')
text = text.replace(r'\`', '`')
text = text.replace(r'\#', '#')
text = text.replace(r'\.', '.')
text = text.replace(r'\-', '-')
text = text.replace(r'\!', '!')
text = text.replace(r'\[', '[')
text = text.replace(r'\]', ']')
text = text.replace(r'\(', '(')
text = text.replace(r'\)', ')')
text = text.replace(r'\~', '~')      # NEW
text = text.replace(r'\|', '|')      # NEW
text = text.replace(r'\&gt;', '&gt;')# NEW (html.escape already turned `>` → `&gt;`; \> arrives as \&gt;)
text = text.replace(r'\+', '+')      # NEW
text = text.replace(r'\=', '=')      # NEW
text = text.replace(r'\{', '{')      # NEW
text = text.replace(r'\}', '}')      # NEW
```

Edge case on `\>`: `html.escape` runs at line 186 BEFORE this strip block, so a literal `>` in LLM output already became `&gt;`. If the LLM emits `\>`, after `html.escape` it becomes `\&gt;`. So we strip `\&gt;` (not `\>`).

**Why not the alternative fixes:**
- Switching to `parse_mode='MarkdownV2'`: would require the LLM to emit valid MarkdownV2 throughout, and the helper currently transforms `**bold**` → `<b>bold</b>` for HTML rendering — flipping mode breaks all that. Big diff, big risk.
- Removing the LLM's escape directive in `prompts.py`: would help once prompt-cache rolls but is a slow rollout, AND would lose escaping for fragments that should be safely literal (e.g., `\.` in dates). Doesn't actually fix the static helper gap.
- The strip-extension is a 7-line addition, confined to one helper, with no behavioral risk to non-escaped text.

### Severity & affected text
- **P0 user-facing visual.** Every Telegram response containing `~`, `|`, `>`, `+`, `=`, `{`, `}` is affected — calorie/protein lists, ranges (`a~b`), tables (`x | y`), comparisons (`>`), simple math (`a + b = c`). The escape `\-` IS already stripped (line 230), so dashes/ranges with `-` are fine.
- Not intermittent. Deterministic for those characters.
- **Does NOT affect:** file uploads, voice messages (those go through `media_sender.py` which doesn't run text through `markdown_to_telegram_html`), bot-generated status messages like "🔄 Annie is thinking..." (no LLM text). Only LLM-text → Telegram rendering is affected.

### Risk of the fix
- **Zero risk to non-escaped text.** `text.replace(r'\~', '~')` only matches the literal two-char sequence `\~`. Ordinary `~` and ordinary `\` followed by other chars are untouched.
- **No collateral.** `markdown_to_telegram_html` is only called from `telegram_bot/handlers/message.py`. `media_sender.py` uses HTML directly with no markdown helper.
- **Pre-existing edge case (not new):** if LLM intentionally emits `\~` *inside a code block* (e.g., a regex example), the strip would still hit it after the `<pre>` wrap. Same already true for `\*`, `\_` etc. Not a new risk; worth a follow-up only if it ever bites.

### Recommendation
**Hotfix it now.** Single-helper, ~8 lines added, no existing tests for this helper (so I'd add one unit test asserting the full MarkdownV2 char set round-trips). Total effort: 1 hour including the test.

**Sample**: 37 Gemini-3.1-pro generations from last 24h via Langfuse SDK (`get_generations`, paged). Pricing rates in `backend/api/observability/cost.py` match Google's published rates exactly ($2/$12/$0.20 per 1M input/output/cached, ≤200K tier).

### Story 23.1 verdict — PASS
Output token / output char ratios sit at **0.23–0.36** across 13 long-output samples (e.g. f5934bca: 111 tok / 459 chars = 0.242, f94a684c: 292 tok / 1031 chars = 0.283). That's the real text-tokenization rate. Pre-fix chunk-count substitution would have produced ~0.04. Output counting is honest. The 30d $12 vs $100 hole was real and is closed for output.

### AC15 verdict — **BUG: 11x overcharge on cached portion** (cache-hit traces only; no-cache traces are correct)
Decoded the cost lines on every 24h trace:
- `costDetails.input` = `prompt_tokens × $2/M` (full input rate on the **entire** prompt — including cached portion)
- `costDetails.output` = `completion_tokens × $12/M`
- `costDetails.total - input - output` decodes to **integer-token counts at the cached rate** ($0.20/M):
  - 1cd04de7: delta $0.004054 → exactly 20,270 tokens @ $0.20/M
  - 9c08f866: delta $0.004066 → 20,330 tokens @ $0.20/M
  - 7d120b0a / 8ba13de3 / a57ff6e1 / 7c219a8f / 087ff905: delta $0.00324 → 16,200 tokens
  - 40760236 / 7d7ea9e5: delta $0.002431 → 12,155 tokens
- These are **real cached_token counts** — AC15 plumbing IS firing. The 24h window doesn't include Murat's earlier 20286-cached traces, but the same shape is everywhere now.

### Root cause
Google's `usage_metadata.prompt_token_count` already INCLUDES `cached_content_token_count` (Google convention — cached tokens are a subset of input tokens, not additive). Annie's emission in `backend/api/providers/gemini_provider.py:1044-1053` builds `input_cost = prompt_tokens × $2/M` (full prompt) AND adds `cached_cost = cached_tokens × $0.20/M`. Langfuse stores `total = input + output + cached`. Net: every cached token is charged at **$2.20/M instead of $0.20/M** — an 11x overcharge on the cached portion, ~5.5x overstatement of total cost on cache-heavy traces.

Worked example (1cd04de7, p=22463 c=41 cached=20270):
- Annie records: `$0.049472`
- Google actually bills: `(22463 - 20270) × $2/M + 20270 × $0.20/M + 41 × $12/M = $0.008932`
- **Annie overstates by 5.5x on cache hits.** No-cache traces (f5934bca, ad684dcf, 84006382, 8d54f54f, etc.) reconcile perfectly.

### Recommendation — open Story 24.2, ~5 LOC fix
In `gemini_provider.py` `_extract_usage_metadata` and the two `end_kwargs["usage"]` blocks (success path ~line 1044, ended-without-stop path ~line 1428), submit `input = prompt_tokens - cached_tokens` instead of `input = prompt_tokens`. Langfuse's `input` field then reflects "non-cached input only", and the `cached_cost` line stops double-counting. Same fix needed in `_trace_error_generation` (line 487) and ChatGPT provider's symmetric block (likely same shape).

Direction of harm: **we OVERSTATE costs in books vs Google billing** when caching is active. Pre-23.1 we understated 8x; post-23.1 we overstate ~5.5x on cache hits. The 30d $12-vs-$100 baseline was 50x output undercount + zero cache instrumentation. Now output is honest, but the cache discount is mis-attributed in the wrong direction.
