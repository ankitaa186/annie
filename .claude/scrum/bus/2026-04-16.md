## [session] Parminder -> team: [DECISION] Scoping decisions for 22.2 follow-on
Parminder (proxied by Fenny):

**A. TTL mechanic — `expireat(eviction_epoch_for_pacific_date(date))`, NOT rolling `expire(30*86400)`.**

Rolling TTL on write breaks the invariant "keys older than 30 days don't exist" — a backfill write to an older date would refresh the clock and keep it alive beyond its natural horizon. Per-key fixed-horizon `expireat` = (the Pacific date in the key at 00:00) + 30 days is deterministic: expiry depends on the date in the key, not the time of the write. Idempotent across re-writes. New helper: `eviction_epoch_for_pacific_date(date_str) -> int`. The existing `next_midnight_pacific_epoch` can be deleted (only caller is the current TTL path).

**B. Fetch tool shape — `get_daily_context(user_id, date=None, days_ago=None)`, single-day.**

LLMs get `days_ago=1` / "yesterday" right far more reliably than they compute date arithmetic. Explicit `date="YYYY-MM-DD"` is the escape hatch. Exactly one of `date` | `days_ago` must be set. `days_ago` range 0-30 (matches TTL horizon). No range param — that's 22.4's job for structured aggregation. On miss, return `{"status":"success","date":...,"scratchpad":null,"found":false}` — LLM must be told to say "I don't have a scratchpad for that day", not hallucinate.

**C. 22.4 verdict — RESHAPE, don't subsume.**

Scratchpad covers the re-ask problem (today + 30-day history). 22.4's value is *structured aggregation* for the 8-week recomp: sum/avg workouts, protein targets, sleep hours. You can't aggregate the prose in `meals`/`mood` slots. 8-week recomp = 56 days, beyond the 30-day scratchpad horizon.

Reshape:
- REMOVE from 22.4: free-text meals / mood / schedule / open_loops / decisions_today (scratchpad owns these).
- KEEP in 22.4: `update_daily_log` for STRUCTURED entries only — workout{type,duration,intensity}, weight{value,units}, sleep{hours,quality}, meal_macros{protein,carbs,fat}, mood_score{1-10}.
- KEEP in 22.4: Redis 90-day hot window + agentic-memories permanence.
- KEEP in 22.4: `get_daily_log(date_range, category)` for aggregation.

22.4 stays P1 deferred. Epic doc needs the reshape. Risk still manageable.

**D. Language sweep — kill "session-scoped".**

- Prompt-injection description: "today-only" or "current day only" (only TODAY appears in [CURRENT_DAY_CONTEXT])
- Storage description: "30-day rolling" (the horizon)
- Never "session-scoped" anywhere — it was already a misnomer pre-30-day (key already crossed TCP sessions), and is actively wrong now.

Files to touch:

**Risk 3 — Key pollution if user_id format changes.** Not a regression — same key schema as 22.2 (`daily_context:{user_id}:{YYYY-MM-DD}`). The new TTL is attached to the same key pattern, so if `user_id` format changes later, the blast radius is identical to 22.2's. Annie's sole user has a stable Telegram numeric `user_id` (1169491032), so practical risk is zero. Approved.

**Risk 4 — Backfill-write extending horizon (invariant violation).** This was the choice between `expire(30*86400)` and fixed-horizon `expireat`. Parminder's choice (fixed horizon via `eviction_epoch_for_pacific_date(date_in_key)`) means a write to `daily_context:{u}:2026-03-20` always expires on 2026-04-19 midnight Pacific, regardless of when the write lands. **Risk 5 — DST at the 30-day horizon.** 30 days crosses a DST transition twice a year. The tests cover both: `test_horizon_crosses_dst_spring_forward` (Feb 20 + 30 = Mar 22, post-spring-forward), `test_horizon_crosses_dst_fall_back` (Oct 15 + 30 = Nov 14, post-fall-back). **Risk 6 — Future-date abuse.** `get_daily_context_tool_handler` rejects future `date` values before hitting Redis. Validated in `test_rejects_future_date` (uses +3650 days for a future-proof assertion). Approved.

**Risk 7 — Corrupt JSON read from Redis.** Both write path (existing — corrupt payload reset to `{}` before write) and new read path (`{found:false}` returned, no crash) are defensive. Validated in `test_corrupt_json_treated_as_miss` and `test_non_dict_payload_treated_as_miss`. Approved.

**Risk 8 — User asks about a day beyond 30-day TTL.** `days_ago` is capped at 30. For explicit `date`, validation accepts older dates but Redis returns nothing (already evicted). Result: `found:false`, LLM tells the user honestly. Acceptable — escalation path would be `retrieve_memories` (permanent facts), which the prompt already directs the LLM to as step 4.

## [session] Parminder -> team: [DECISION] 22.2.2 design — free-form keys with guardrails
Parminder (proxied by Fenny):

**A. Shape: fully free-form `update_daily_context(user_id, key, value)`.**
LLM picks semantic names. Storage model unchanged: flat JSON dict `{key: str, ...}` under the existing `daily_context:{user_id}:{YYYY-MM-DD Pacific}` Redis key. No schema migration. Existing 2026-04-16 scratchpads in Redis already look like `{"meals": "...", "schedule": "..."}` — those keys are valid under the new validator, so the LLM just keeps using them naturally.

**B. Key validation regex: `^[a-z][a-z0-9_]{0,31}$`.**
- Lowercase letters, digits, underscore; start with a letter; max 32 chars.
- Rejects: whitespace, punctuation, emojis, colons (would collide with Redis key structure), dots, spaces, uppercase (prevents `Meals` vs `meals` drift), leading digits.
- No silent normalization — explicit VALIDATION_ERROR with the regex in the message. The LLM should learn, not have magic renaming applied.
- Rationale: drift mitigation without being prescriptive. If the LLM wants `house_hunting_options`, that's fine. If it wants `House Hunting!`, it gets told no and retries.

**C. Per-key value cap: 2000 chars (unchanged — rename `MAX_SLOT_CHARS` → `MAX_VALUE_CHARS`).**
Truncate, don't reject — preserves "partial > nothing" from 22.2.

**D. Per-day key-count cap: 20 keys.**
- Prevents LLM chatter-key bloat (e.g., creating `breakfast`, `lunch`, `snack_1`, `snack_2` instead of appending to `meals`).
- When a write would push the count over 20, reject with error_code `KEY_LIMIT_EXCEEDED` and a message telling the LLM to reuse/consolidate an existing key. Updates to an EXISTING key are always allowed (the count doesn't change).
- 20 * 2000 = 40 KB max scratchpad in the prompt. Acceptable cost.

**E. Rendering order: insertion order (Python dict native).**
- Python dicts have preserved insertion order since 3.7. Redis stores the JSON-serialized dict, and `json.loads` preserves key order. So "the order the LLM first wrote keys today" is what ends up in the prompt.
- Feels natural — the thing the user told Annie FIRST stays rendered FIRST, like a journal.
- No sorting — alphabetical would put `bedtime` before `schedule` which is semantically arbitrary. LLM-specified priority would require a schema change for negligible value.

**F. Deletion: no dedicated tool.**
- `update_daily_context(key, value="")` effectively clears via `format_for_prompt`, which strips blank/whitespace values (already tested in `test_all_blank_values_returns_empty_string`).
- Document this in the tool description so the LLM knows. Adding an explicit `clear_key` tool is ceremony that saves one empty string from being sent.
- The key REMAINS in the JSON dict after a clear (just with empty value). That's fine — it still counts toward the 20-key cap for the day, which is honest: "you created this key, even if it's now empty, it's a used slot."

**G. Back-compat: none needed.**
- Keys currently in Redis (`meals`, `schedule`, etc.) all pass the new regex.
- No in-prod keys to migrate because 22.2 was never deployed to Ankit's live environment (it's on uncommitted develop).
- Even if they were — the LLM just keeps reading/writing them; no code path cares about the value space anymore.

**H. Code-shape changes:**
- `mcp_server/tools/daily_context.py`: remove `ALLOWED_SLOTS`, rename `MAX_SLOT_CHARS`→`MAX_VALUE_CHARS`, add `_KEY_REGEX` + validator, add `MAX_KEYS_PER_DAY = 20` + check, rewrite tool schema (drop enum, add `pattern` + `maxLength` on `key`), rewrite tool description. Param name `slot`→`key` everywhere (LLM-facing + handler).
- `backend/api/daily_context.py`: remove `DAILY_CONTEXT_SLOTS`, rewrite `format_for_prompt` to walk `scratchpad.items()` directly in insertion order. No slot-iteration.
- `backend/api/prompts.py` MEMORY_MANAGEMENT_SECTION: replace slot-specific trigger list with "pick a clear snake_case key that names the fact"; show 3 example keys for variety; document clearing via empty string.
- Epic doc §22.2: slot list → "free-form keys" paragraph; add §22.2.2 scope paragraph.

**I. 22.4 rationale: unchanged.**
Scratchpad is still prose. 22.4 is still numeric/structured aggregation over 90-day horizon. Generalizing keys doesn't change the boundary.

## [session] Harpreet -> team: [REVIEW] 22.2.2 — risks reviewed, approved
Harpreet (proxied by Fenny):

**Risk 1 — LLM key-drift (`meals` vs `food_today` vs `breakfast` across days).**
Mitigated structurally:
(a) Prompt guidance explicitly says "reuse existing keys from [CURRENT_DAY_CONTEXT] — don't proliferate siblings like `breakfast`+`lunch` when `meals` exists." Explicit convergence pressure.
(b) LLM sees the existing day's keys in every turn via the rendered block, so the cheap thing is to reuse.
(c) `get_daily_context(days_ago=N)` returns the full dict for any past day, so even if day-to-day keys drift, the LLM sees whatever keys that specific day used and works with them. No query-by-key surface area to break.
(d) 20-key cap creates additional pressure against chatter.
Accepted cost: across 30 days, yes, the LLM might use slightly different keys on different days. Ankit's workflow is "ask about yesterday/last week" — the tool returns the full dict, the LLM reads it, the LLM answers. Zero structural dependency on cross-day key consistency.
Approved.

**Risk 2 — Token bloat from chatter keys.**
Mitigated at three layers:
(a) 20-key cap (`KEY_LIMIT_EXCEEDED`) is a hard ceiling. 20 * 2000 chars = 40 KB scratchpad max.
(b) Error message on cap breach lists currently-set keys and tells the LLM to consolidate. Educational, not punitive.
(c) Prompt convention "reuse existing keys" reduces key-count growth in the first place.
Approved.

**Risk 3 — Arbitrary string key in Redis (security / injection).**
Non-risk. The validator regex `^[a-z][a-z0-9_]{0,31}$` rejects every character class that could cause trouble (colons / slashes / newlines / whitespace / unicode). The Redis key itself is still `daily_context:{user_id}:{date}` — the LLM-chosen key is a DICT KEY inside the serialized JSON value, not part of the Redis key string. Even if the regex were looser, `json.dumps` escapes whatever's in it before it hits Redis. Double-defended.
Approved.

**Risk 4 — No silent normalization means `Meals` vs `meals` are distinct if the LLM slips.**
The choice is between silent lowercasing (LLM never learns) vs strict rejection (LLM learns on first write). Strict rejection wins for a sole-user sophisticated-LLM setup — the error message contains the regex, so the LLM corrects on the next tool call. Grok-4 / ChatGPT-5 / Gemini all self-correct on tool-call errors in the SAME turn when validation errors are descriptive.
Approved.

**Risk 5 — Empty-string-clears mechanism isn't a real delete.**
Explicit design choice — keeps the key in the dict (still counts against the 20-key cap) but strips it from the rendered prompt. Means the LLM can't infinitely recycle slot real estate by clearing and re-creating. Matches the "no wasted slots" intent of the cap. If Ankit ever wants a true delete we can add one, but a sole-user scratchpad with a 20-key/day ceiling doesn't need it.
Approved.

**Risk 6 — Back-compat for existing 22.2 Redis data.**
Checked: all six former enum values (`schedule`, `meals`, `workout`, `mood`, `open_loops`, `decisions_today`) pass the new validator. No live keys were written with hyphens / dots / uppercase / etc. (because the old enum wouldn't have accepted them). Zero migration.
Approved.

Approved across the board. Moving to Murat for the green.
